# Autonomous ZSK factory simulation

Original Phaser/React side-view environment, authoritative FastAPI state, independent Factory MCP, continuous PostgreSQL measurements, current-health RandomForest and separate future-onset baseline, durable alarm delivery into the existing Meta-Harness task engine. **Simulation only. No PLC, real actuator, machine-control adapter or physical equipment connection exists.** `ZSK-SIM-01` is an illustrative synthetic machine, not a manufacturer-validated configuration.

The two user-supplied lab images informed the teal panels, dark outlines, orange machine details and side view; no reference assets are copied. The scene is original procedural Phaser art.

## Start

Requirements: Docker/Compose, existing root `.env`, initialized current `zsk-service` database/model, configured OpenAI model and enabled/allowlisted RAG MCP with relevant documents. Do not restart historical `manufacturing-demo/` against the replaced database. Preserve its existing manufacturing database password and volume.

1. In root `.env`, create distinct random values (at least 24 characters) for `FACTORY_API_TOKEN`, `FACTORY_MCP_AUTH_TOKEN`, `TASK_INTEGRATION_TOKEN`; also set `FACTORY_TEST_DB_PASSWORD` before isolated tests. Use `.env.example` for names, never copy it over an existing `.env`. `chmod 600 .env`. These values are never passed to UI assets.
2. Add `http://factory:8110` to root `MCP_ALLOWED_ORIGINS`; set `FACTORY_API_URL=http://factory:8110` and `FACTORY_ALLOWED_ORIGINS=http://factory:8110,http://127.0.0.1:8110`.
3. Run from the repository root:

```bash
docker network inspect meta-harness-mcp >/dev/null 2>&1 || docker network create meta-harness-mcp
docker compose --env-file .env -f zsk-service/docker-compose.yml -f zsk-service/docker-compose.meta-harness.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.mcp.yml -f docker-compose.factory.yml up -d --build
docker compose --env-file .env -f factory-service/docker-compose.yml up -d --build
```

The ML image must be built before the factory image, which reuses its pinned Python dependencies. PostgreSQL remains on private Docker networks. UI is `http://127.0.0.1:8080`; core `8000`, ZSK `8100`, factory `8110`, all host bindings loopback. Existing RAG stack startup remains in `rag-server/README.md`.

4. Register through **MCP → Add MCP Server**: URL `http://factory:8110/mcp`, credential environment variable `FACTORY_MCP_AUTH_TOKEN`. Discover tools and explicitly allowlist read-only tools and requested simulation diagnostics. A write tool annotation alone does not authorize a task grant.
5. The operator-run setup script registers/reuses the generic profile, discovers its schema, configures permitted diagnostic tools and task grants, adds the two read-only forecasting tools to the existing ML profile, and writes only root `.env`:

```bash
python3 factory-service/scripts/configure.py --rag-device-id EXISTING_RAG_DEVICE_UUID
# Explicit optional authorization for the requested autonomous simulated-stop demonstration:
python3 factory-service/scripts/configure.py --rag-device-id EXISTING_RAG_DEVICE_UUID --demo-stop
docker compose -f docker-compose.yml -f docker-compose.mcp.yml -f docker-compose.factory.yml up -d --force-recreate core
docker compose --env-file .env -f factory-service/docker-compose.yml up -d --force-recreate
```

The script requires exactly one enabled RAG profile with allowlisted `search_knowledge`. The RAG UUID must identify the existing extruder documentation asset. This mapping is explicit demonstration configuration, not evidence of a physical machine identity. No RAG data/schema is modified. Missing factory secrets can be generated by this script; for first startup, supply them before step 3.

## Operate

Sidebar **FACTORY** is independently collapsible; its pages preserve the existing chat/draft: **Factory Simulation**, **Machine Monitoring**, **Alarms**, **Simulation Settings**. The scene is the primary element. Click a component for its signals, condition, inspection and technician action. **Send technician** starts an actual backend diagnostic action.

The clock supports **Pause/Resume**, **1×/5×/10×/60×** and a confirmed **Reset**. Five-minute measurements and ten-minute monitoring use simulated time. At 60×, ten simulated minutes take ten wall seconds. Closing the browser does not stop the worker. Container downtime freezes the clock; it does not fabricate operating time. Reset creates a new episode, retains all historical data/actions, advances no time backward, and starts paused. Old-episode MCP actions are rejected.

Monitoring shows all ten stored signals, both timestamps, separate current classification/future-onset output, versions and retry status. **Alarms** shows the incident, saved model evidence, task status/latest tool, operator report and task-history link. Task history opens the existing task UI, including operation results, immutable criteria, exact approvals and reconciliation. Failed tasks can be retried there; UNKNOWN writes require external reconciliation before resume. Do not resume an old-episode task after resetting.

**Simulation Settings** allows clearly marked manual fault injection: gearbox vibration, bearing deterioration, excessive screw torque, oil overheating, barrel instability, high melt pressure, unstable feeding and excessive current; gradual/sudden progression. Automatic faults are toggleable. Scenarios correlate load, torque/current/power, vibration/oil temperature and flow. Their ranges/signatures are synthetic assumptions, not Coperion specifications. Explicitly confirmed operator stop/restart/repair/reset use the separate operator credential through core. Maintenance requires stopped production, prior inspection and completed technician movement; repaired signals recover gradually. Restart rejects severe faults or pending actions.

## Automatic demonstration

Use `--demo-stop` setup and recreate services. In Simulation Settings, reset first; the line must be running in its fresh episode with no faults. Then:

```bash
python3 factory-service/scripts/demo.py
```

This injects gradual gearbox deterioration at 60×. It **never invokes the LLM or task-creation endpoint**. The worker owns sampling → periodic ML → persisted alarm/outbox → authenticated task event. The existing task engine reads measurements/model evidence, queries actual RAG, executes its explicitly granted simulated stop/inspection, polls completion, verifies six immutable predicates and writes the operator report. The script observes actual progress and saves `docs/verification/factory/end-to-end.json`; a timeout/failure is recorded honestly. Model/API availability and reasoning time can delay completion.

## Permissions and secrets

All three automatic controlled-action defaults are **false**:

```dotenv
SIMULATION_AUTO_STOP_ALLOWED=false
SIMULATION_AUTO_RESTART_ALLOWED=false
SIMULATION_AUTO_MAINTENANCE_ALLOWED=false
ML_MONITOR_INTERVAL_MINUTES=10
FACTORY_AUTOMATIC_FAULTS=true
```

An action needs both operator allowlist/task grant and factory policy. `--demo-stop` explicitly enables only stop/pause-line; restart/maintenance remain disabled. Higher-risk simulation permissions must be explicitly configured; prompts cannot grant them. No policy setting authorizes physical machine control. Read-only tools and diagnostic grants can investigate without further operator interaction. The internal event credential can select only tracked templates and their fixed grants; it cannot submit an arbitrary task, filesystem command or validator.

`FACTORY_API_TOKEN` is for core→operator REST/WS; `FACTORY_MCP_AUTH_TOKEN` for MCP; `ZSK_API_KEY` for read-only ML; `TASK_INTEGRATION_TOKEN` for scoped template events; existing `MANUFACTURING_DB_PASSWORD` for private DB. Root `.env` remains ignored. Browser sees no token. Compose injects only relevant credentials. Error logs use bounded generic messages. MCP request schemas forbid unknown fields. HTTP authentication rejects unauthorized/wrong-scope tokens. Core validates fixed factory destinations/DNS and local origin, and proxies WebSockets with bounded payload/backpressure.

## MCP tools (17)

Read: `get_factory_state`, `get_machine_state`, `get_machine_measurements`, `get_machine_alarms`, `get_monitoring_results`, `list_factory_components`, `list_factory_characters`, `get_factory_action_history`, `get_maintenance_status`.

Simulation writes: `move_character`, `inspect_component`, `stop_manufacturing_line`, `start_manufacturing_line`, `pause_manufacturing_line`, `acknowledge_alarm`, `assign_maintenance_task`, `perform_simulated_maintenance`.

State-changing machine/technician tools require the current `epoch`. Harness `Idempotency-Key`/MCP `_meta.operationId` takes precedence over an optional model-provided key. Standalone callers must supply a stable key. Responses return committed action ID, previous/new state, timestamp, evidence and status; **accepted is not completed**. `get_maintenance_status` can require epoch/component/alarm identity, preventing reuse of an unrelated old inspection.

## ML limitations

The original current classifier is unchanged: 0=Faulty, 1=Healthy, same causal rolling features. New readings go into unlabeled rows; predictions and simulator truth have separate tables. Purged historical labels are never re-seeded or reconstructed from predictions.

The separate forecast learns **future simulated fault onset**, not remaining useful life. It uses reproducible synthetic episodes, 20 existing causal features, three five-minute readings, forward labels at severity ≥0.7, chronological holdout and a horizon/history embargo. Already faulty targets are excluded during training and do not receive future-onset inference in the monitoring worker. Incomplete horizons are censored. Episode boundaries/cadence mismatches enter warm-up. Changing `ZSK_FORECAST_HORIZON_MINUTES` (multiples of 5, 5–120) and recreating ML trains/validates a new registered artifact and atomically activates it; holdout is never refit. Disable bootstrap with `ZSK_FORECAST_BOOTSTRAP=false` to retain the active artifact. Probabilities are uncalibrated.

Measured 30-minute synthetic baseline: train 835, holdout 200, nine raw rows embargo; onset precision 0.808, recall 0.700, F1 0.750, balanced accuracy 0.835; confusion matrix `[[165,5],[9,21]]`. See actual versioned `forecast-metrics.json`. These metrics validate this simulator baseline only. No industrial prognosis, mechanical diagnosis, official operating limit or validated maintenance procedure is claimed.

Authoritative engineering details: [FACTORY_ARCHITECTURE.md](../docs/FACTORY_ARCHITECTURE.md). Real-provider execution evidence is separate from deterministic fixtures and initial failed attempts.
