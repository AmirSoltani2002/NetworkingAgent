# Current Data Models

PostgreSQL is the source of truth for saved conversations and attached file bytes. [database/schema.sql](../database/schema.sql) is the canonical schema. The generic MCP registry is implemented; RAG connection metadata reuses it; durable task tables are implemented; domain-specific analyzer/workflow-template tables remain absent. OpenAI configuration is persisted in .env, not new database tables.

Database/application connection credentials are configuration, not chat data. Passwords, tokens, API keys, and future confidential connection settings belong in the ignored root .env. Future profiles must persist only the corresponding environment-variable reference, never the raw secret. PostgreSQL still maintains its own authentication record for the initialized database user. See [OPERATIONS.md](OPERATIONS.md).

## chats

| Column | Definition |
| --- | --- |
| id | UUID primary key generated by core |
| title | Required text, initially New chat |
| created_at | Required timestamptz, defaults to now() |
| updated_at | Required timestamptz, defaults to now(); updated by a new message |
| context_window | Nullable private JSONB: model ID, complete model input items (including opaque compaction/reasoning and tool results), and throughPosition message watermark; never returned to the browser |

List order is updated_at descending, then id. The first successfully saved message sets the title. Core collapses whitespace in message text for the title; if there is no text, it uses the first uploaded filename. Titles longer than 48 Unicode code points become the first 47 plus an ellipsis. Later messages retain the title. There is no LLM title call or rename endpoint.

New chat in the UI starts an unsaved draft. POST /api/chats creates the row when sending begins; an upload failure can leave an empty chat with the default title.

The model window and assistant reply commit together. Later prompts append only messages newer than throughPosition, preventing duplicate input. Model changes rebuild from the visible transcript. Compaction replaces model input, never stored messages. Mid-turn compacted state remains in messages.tool_state until completion. Known saved secrets are redacted from plaintext provider/tool context; opaque encrypted items pass back unchanged.

## messages

| Column | Definition |
| --- | --- |
| id | UUID primary key: clientMessageId for users, generated by core for assistants |
| chat_id | Required chats foreign key, ON DELETE CASCADE |
| position | Generated bigint identity used for stable message order |
| role | Required text, default user; constraint permits user or assistant |
| reply_to_message_id | Nullable messages foreign key, ON DELETE CASCADE; unique when non-null |
| tool_calls | JSONB array of bounded server/tool/success/duration/source-reference metadata; default [] |
| tool_state | Nullable private JSONB for bounded pending confirmation/provider continuation and already-executed results; never returned to browser |
| text | Required text; core trims outer whitespace; empty text is valid with files |
| created_at | Required timestamptz, defaults to now() |

Assistant replies use role assistant and reference the answered user through reply_to_message_id; a unique partial index permits at most one saved reply per target. User rows have null linkage. Existing user-only histories remain valid; reopening the latest unanswered user offers response retry. An index on (chat_id, position) supports ordered history reads.

A retry with the same valid message UUID in the same chat returns the original saved message. It does not update text, files, title, or timestamps. Editing the draft creates a new submission UUID. UUIDs must be unique across all messages; they are not general update keys. tool_state is cleared on a new user turn or completed assistant reply; a pending confirmation is exposed only as a bounded public summary. Interrupted external execution is never automatically replayed.

## attachments

| Column | Definition |
| --- | --- |
| id | UUID primary key generated by core |
| message_id | Required messages foreign key, ON DELETE CASCADE |
| position | Required integer preserving upload order |
| name | Required filename; core replaces slash, backslash, CR, LF, and NUL with underscores, truncates to 255 UTF-16 code units |
| size | Required nonnegative integer, byte count |
| content | Required bytea containing the uploaded bytes |

An index on (message_id, position) supports attachment reads. Attachment bytes stay in PostgreSQL, not in an object-storage service or a host upload directory. Metadata lists omit content; download URLs return binary attachments.

## Transaction and initialization rules

A message insert, all attachment inserts, and the chat activity/title update commit together. Core locks the chat row before checking for an existing submission. Failed transactions roll back these changes.

PostgreSQL initializes a fresh data directory from schema.sql. Core reapplies its idempotent statements under an advisory transaction lock on startup. The explicit ADD COLUMN IF NOT EXISTS upgrades existing volumes with reply linkage; CREATE TABLE alone cannot change existing tables. Core now applies checksum-protected ordered SQL migrations and records them in schema_migrations. Cascade relationships are defined in SQL, but the API provides no delete route.

User saves acquire a per-chat advisory transaction lock; response requests hold the matching session lock across inference, without a long SQL transaction. Concurrent requests get 409. Assistant insertion/activity/context update commit together. An existing reply is returned without another OpenAI call; only the latest unanswered user may receive a new reply. Failures create no assistant row. A crash between provider completion and database commit can require another paid request; exactly-once provider billing is not guaranteed. Provider conversation IDs are not used; encrypted reasoning/compaction items persist in the private model window. Tool metadata is recorded on the user during calls (including failed provider attempts), and copied to a successful reply. Arguments, passage content and credentials are excluded from public traces; private context/checkpoints retain necessary tool data. This is not immutable workflow history.

## JSON representations

API fields use camelCase. Timestamps serialize as ISO date/time strings. ChatSummary contains id, title, createdAt, updatedAt. ChatDetail adds messages. Each message includes id, role, text, createdAt, replyToMessageId, attachments, and toolCalls. Attachment metadata contains id, name, size, and downloadUrl.

The UI consumes id, role, text, replyToMessageId, and attachments, rendering user bubbles and assistant plain text. Timestamps are not displayed. PendingAttachment holds a browser File and temporary UUID until submission.

Examples, size limits, and response envelopes are owned by [API_SPEC.md](API_SPEC.md). Future persistence requirements are in [ROADMAP.md](ROADMAP.md).

## LLM configuration outside PostgreSQL

| .env entry | Type/use |
| --- | --- |
| OPENAI_API_KEY | Secret, never returned in full; GET exposes a four-character prefix plus stars |
| LLM_PROVIDER | openai |
| LLM_MODEL | Selected remote model ID, or empty when unselected |
| LLM_THINKING | instant, medium, high; default medium |
| LLM_CONTEXT_WINDOW_TOKENS | Optional operator-set token capacity for the selected model; defaults and compaction behavior are owned by OPERATIONS.md |

A public configuration response contains provider, hasApiKey, maskedApiKey, model, and thinking. Raw key values are accepted only by the write-only entry field and stored server-side. Existing ANALYZER_* entries from older specifications are preserved but are not used by this feature.

## Generic MCP registry

`mcp_servers`: UUID `id`; `name`; unique `url`; nullable `auth_env_var` reference; operator `description`; `enabled`, `agent_enabled`, `disconnected`; JSONB `tools` (name, description, readOnly annotation, inputSchema); text-array `allowed_tools`; `status` (unconnected/connected/failed); sanitized `last_error`; `discovered_at`, `created_at`, `updated_at`. Credentials are never stored in rows. Connection changes clear discovery/allowlist metadata; refreshing tools removes obsolete selections. No workflow/run table is added.

The standalone RAG uses a **separate database** with six domain tables and Alembic version bookkeeping. Its authoritative schema/migration and model-contract description is [rag-server/README.md](../rag-server/README.md), not the chat schema. Chat files are not automatically ingested there.

## RAG profile metadata in the existing registry

Idempotent schema upgrades add `rest_url`, independent `rest_status` (unconfigured/connected/failed/disconnected), `rest_error`, `rag_enabled`, `agent_enabled`, `disconnected` and discovered `server_name` to mcp_servers. Existing registrations remain selectable in RAG; their REST URL must be supplied explicitly. Disconnect retains credentials/metadata but prevents calls. Saving resets connectivity and disables agent access; tool selections are retained only for unchanged MCP URL/credential references. No devices, issues, manuals, chunks, vectors or evidence-link rows are replicated here.

Write-only bearer tokens live in generated `MCP_TOKEN_<UUID_WITHOUT_HYPHENS>` root .env entries; the SQL row references that variable. Existing environment references are reused without reentering credentials. Removing a registry row does not delete secrets that another profile may reference.

## Durable tasks

Tasks, steps, operations, approvals, verification results, progress events and schedules persist in this same database. Trigger/incoming-event tables are historical and inactive while event triggers are removed. Private task model context is excluded from public responses. Each conversation/message can own tasks; message identity and occurrence/event keys prevent duplicates. Migration 001 adds persistence, 002 adds optional cost accounting and 003 adds private context_state delivery fingerprints, prompt_tokens_start/prompt_turns_start/prompt_active_start budget baselines and continuation_count. Lifetime usage remains cumulative; context_state is excluded from public responses. Table fields, state transitions and concurrency contracts are owned by [TASK_EXECUTION.md](TASK_EXECUTION.md).

Task operation kind `response` stores the selected model’s answer as `{text,externalExecutionVerified:false}` with internal policy identity. A response-only completion criterion validates nonempty delivery; existing external completion predicates remain immutable. No schema upgrade is needed because operation/criterion kinds are stored as text/JSON.

Task operation kind `evidence` records bounded reads of this task’s already persisted operation results. It is internal, read-only, requires no external permission, and is not an eligible external completion-criterion kind.

## ZSK external manufacturing data

Dedicated manufacturing DB now uses supplied zsk_labeled_measurements (empty after training), zsk_unlabeled_measurements (1,000 initial readings), zsk_predictions, zsk_jobs, zsk_models, zsk_state, zsk_requests, zsk_audit, zsk_job_predictions and checksum migrations. Predicted labels remain separate. Initial legacy manufacturing_products/evaluation_products are removed after validated activation; old training_jobs metrics history remains. No chat database schema changes. Details in zsk-service/migrations and README.

## Factory extension

Core additive migration `004_task_integrations.sql` adds `task_integration_receipts(source,event_id,fingerprint,task_id,created_at)`, primary key `(source,event_id)`, FK to existing tasks. It atomically binds authenticated template events to durable tasks. Historical generic trigger tables remain inert.

Factory domain tables live only in the existing manufacturing database, through `factory-service/migrations/001_factory.sql`; their ownership/relationships are listed in [FACTORY_ARCHITECTURE.md](FACTORY_ARCHITECTURE.md). New sensor values append to current ZSK unlabeled rows. Ground truth and predictions remain separate. `zsk-service/migrations/004_forecast.sql` adds versioned future-onset artifacts/metrics. No RAG domain tables are added or changed.
